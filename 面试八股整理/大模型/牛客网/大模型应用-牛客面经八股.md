## 1. 把 Transformer / Decoder‑only 的整体结构过一遍，各个组件分别在干什么，有哪些常见变体。
**【一句话总结】**
 
Transformer/Decoder-only 结构是一个**基于自回归建模的堆叠式神经网络**，其核心是通过**掩码自注意力（Masked Self-Attention）和前馈网络（FFN）** 层层堆叠，配合残差连接与层归一化，实现对序列数据的强大表征和生成能力；常见变体主要在**注意力机制、位置编码和激活函数**上进行优化，以提升效率、稳定性和长程依赖处理能力。

---

#### **详细解析：核心组件与工作流程**

 Decoder-only 模型（如 GPT 系列）是原始 Transformer 的解码器部分，专为自回归生成任务设计。

 **1. 核心组件与功能** 

| 组件 | 功能与作用 | 为什么重要 |
| --- | --- | --- |
| 输入嵌入（Input Embedding） | 将离散的 token 转换为密集的向量表示。 | 将符号信息转化为数值形式，供模型处理。 |
| 位置编码（Positional Encoding） | 为 token 注入位置信息（如正弦波、学习式编码）。 | Transformer 本身无时序概念，此组件是理解顺序的关键。 |
| 掩码自注意力层（Masked Self-Attention） | 核心组件。让每个 token 只关注它之前的 token（包括自己），计算加权和。 | 实现并行训练的同时，严格保证自回归生成的特性（看不到未来信息）。 |
| 前馈网络（FFN） | 对每个位置的表示进行独立的非线性变换（通常是两层线性层+激活函数）。 | 引入模型所需的非线性能力和表征多样性。 |
| 残差连接（Add） | 将某一层的输入直接与其输出相加。 | 缓解深层网络的梯度消失问题，使网络可以堆叠得很深。 |
| 层归一化（Norm） | 对激活值进行标准化（通常放在 Attention 和 FFN 之前，即 Pre-Norm）。 | 稳定训练过程，加快收敛速度。 |

 **工作流程（以生成一个 token 为例）**：

 - **输入处理**：输入序列经过Embedding和Positional Encoding，得到融合了词义和位置信息的向量。

 - **注意力计算**：向量进入Masked Self-Attention层，每个 token 与它之前的所有 token 进行交互，聚合上下文信息。

 - **非线性变换**：注意力输出送入FFN，在每个特征维度上进行独立变换，增强模型能力。

 - **残差与归一化**：上述每一步都包裹着Add & Norm，确保信息流畅和训练稳定。

 - **循环堆叠**：步骤 2-4 重复 N 次（如 GPT-3 的 96 层），实现深层次的特征抽象。

 - **输出预测**：最后一层的输出经过一个线性投影层和 Softmax，得到下一个 token 的概率分布。

 **2. 常见变体及其改进方向** 

 研究人员对原始结构进行了大量改进，主要围绕效率、能力和稳定性。

| 变体类别 | 代表方案 | 解决了什么痛点 |
| --- | --- | --- |
| 注意力机制优化 | FlashAttention | 通过减少 GPU 内存读写次数来大幅加速计算并降低内存占用，是当前训练大模型的工程标配。 |
| 位置编码扩展 | RoPE (旋转位置编码) | 将位置信息编码在旋转矩阵中，天生具有更好的外推性（能处理比训练时更长的序列），被 LLama、GLM 等主流模型采用。 |
| 归一化层改进 | RMSNorm | 去掉了 LayerNorm 中的均值中心化，计算更简单，效果相当甚至更好，被 LLama 等模型采用以提升效率。 |
| 激活函数替换 | SwiGLU | 替换原始的 ReLU/GELU，被证明能显著提升模型性能，但会增加参数量和计算量。是现代模型（如 PaLM）的常见选择。 |
| 架构简化 | Parallel Attention/FFN | 将 Attention 层和 FFN 层并行计算，而不是串行，减少层数，降低延迟（如 Google 的 PaLM 模型）。 |

---

#### **总结**

 - **核心思想**：Decoder-only 模型是一个**强大的特征提取器+生成器**。通过**掩码自注意力**捕获上下文，通过**FFN**进行非线性变换，通过**残差和归一化**保证训练稳定性，最终通过**堆叠**获得强大能力。

 - **变体目的**：所有变体都旨在**效率、能力、稳定性**这三个维度上寻求更优的平衡。

## 2. 位置编码这条线你怎么选：绝对 PE、相对 PE、RoPE 各自的思路、优势和局限，结合你的项目谈取舍。
【一句话总结】
 
我根据**任务对位置信息的敏感度、序列长度需求和计算开销**来选：**绝对PE**用于简单短序列任务（如分类），**相对PE**用于对位置关系敏感的任务（如音乐生成），**RoPE**因其强大的外推性和性能成为长序列、生成式任务（如LLM、长文本处理）的首选。

---

#### **详细解析：三种位置编码的对比与取舍1. 绝对位置编码 (Absolute PE)** 

 - **思路**：为序列中的每个绝对位置（如第1个词、第2个词）分配一个固定的或可学习的向量表示，然后直接与词向量相加。

 - **优势**： **实现简单**，直观易懂，计算开销小。

 - 在**序列长度固定**且与训练时一致的场景下非常有效。

 - **局限**： **长度外推能力差**：模型无法处理比训练时更长的序列，性能会急剧下降。

 - **无法直接表征相对位置关系**：模型需要额外学习“位置i和位置j的关系”。

 - **项目取舍**：在我早期的一个**文本分类项目**中，所有文本都被截断/填充到固定长度（512），且没有长序列推理需求，我选择了**可学习的绝对PE**。因为它简单可靠，完全满足需求，没有引入不必要的复杂性。

 **2. 相对位置编码 (Relative PE)** 

 - **思路**：不关注词的绝对位置，而是关注词与词之间的**相对距离**（如偏移量△ = i-j）。将这种相对位置信息编码成一个偏置项，添加到注意力评分中。

 - **优势**： **更好的泛化性**：理论上可以处理任意长度的序列，因为模型关注的是相对距离，而非绝对位置。

 - **对局部关系和语序更敏感**：尤其适合需要精细理解词与词之间关系的任务，如音乐生成、代码生成。

 - **局限**： **实现复杂**：计算相对距离偏置并高效地集成到注意力机制中（如T5的实现）比较复杂。

 - **计算开销稍大**：需要计算所有位置对的相对关系。

 - **项目取舍**：在一个**音乐生成项目**中，音乐的音符间关系（和弦、节奏型）严重依赖于相对位置。我们采用了**T5风格的相对位置编码**，因为它能更好地建模这种局部和全局的依赖关系，生成的音乐片段在结构上更连贯。

 **3. 旋转位置编码 (RoPE)** 

 - **思路**：通过一个**旋转矩阵**对查询（Q）和键（K）向量进行变换，使得它们的点积结果天然包含了相对位置信息。即，通过“旋转”向量来编码位置。

 - **优势**： **同时具备绝对和相对位置的优点**：在短序列上表现良好，同时拥有**极佳的长度外推能力**。可以通过微调甚至零样本的方式处理远长于训练时的序列。

 - **理论优雅，实现高效**：巧妙地融入了注意力计算本身，无需修改注意力公式。

 - **局限**： **目前被视为主流和大模型首选**，几乎没有明显缺点，是其设计上成功的体现。

 - **项目取舍**：在构建**企业内部知识库的QA系统**时，我们需要处理长达数万token的长文档。基于**LLama架构（采用RoPE）** 微调模型是最自然的选择。RoPE的强大外推能力允许我们在训练时使用较长的上下文（如4k），而在推理时轻松处理更长的文档（如16k），完美满足了项目需求，避免了复杂的滑动窗口等技巧。

#### **总结与选型建议**

| 编码类型 | 首选场景 | 一句话建议 |
| --- | --- | --- |
| 绝对PE | 序列长度固定、简单的理解类任务（文本分类、情感分析） | 如果序列长度不变且任务简单，它是简单可靠的基准选择。 |
| 相对PE | 对相对位置关系高度敏感的任务（音乐、代码、蛋白质序列生成） | 当任务的本质是建模元素间复杂关系时，它是强大的工具。 |
| RoPE | 生成式任务、长文本处理、大型语言模型（LLM） | 现代项目的默认起点，尤其在长度需求不确定时，它提供了最大的灵活性和性能。 |

 **最终建议**：如今，**RoPE**因其卓越的外推性能和已成为事实标准的地位，应作为大多数新项目的**默认选择**。只有在有非常明确的理由（如追求极致的简单性或有特定领域需求）时，才考虑绝对PE或相对PE。

## 3. Tokenizer（BPE、SentencePiece）你是怎么落地的？词表、OOV、计费与上下文规划都怎么处理。
**一句话总结** 

 训练时用 SentencePiece（中英多语优先 Unigram，纯英文/代码可用 BPE）在统一清洗后的大语料上产出稳定词表，线上用“字节/子词回退+保留特殊符号+版本固化”基本杜绝 OOV；计费与上下文则用同一分词器预估 token 数，按“系统/用户/检索/回复”分区预留与截断，确保不超窗又不浪费。

 **详细解释：** 

 - 词表与训练 语料先做规范化（NFKC、统一空白/标点、大小写策略），中英文混合优先 SentencePiece‑Unigram；纯英文/代码用 BPE 更高效。

 - 设 vocab_size=32k/50k（业务与显存权衡），character_coverage≥0.9995，加入特殊符号与业务自定义标记（工具调用、域内占位符）。

 - 命令示例：spm_train --model_type=unigram --vocab_size=50000 --character_coverage=0.9995 --user_defined_symbols=[…]。

 - OOV 与鲁棒 启用 byte‑fallback/byte‑BPE 或者覆盖常见 emoji/稀字符，基本无 UNK；必要时 piece‑dropout 提升鲁棒。

 - 中文场景可“字级+子词混合”降低分词碎片化；新词热启动用追加训练或热词白名单直通。

 - 计费与上下文规划 用同一 tokenizer 预估 token，建立配额函数：系统指令/工具模式/用户输入/检索上下文/模型回复分别预留（例如 8k 窗口：sys 0.5k + tools 0.5k + ctx 动态 ≤5k + reply 2k）。

 - 超长内容按优先级截断：先压缩低权重段，再做语义摘要或检索切片（map‑reduce）；保证不超窗同时减少无效 token。

 - 和供应商计费规则对齐（按 token 计费），上线前做 tokens/char 比率基线（中文≈1.8‑2.2，英文≈0.75‑1.0）便于成本估算。

 - 工程落地 线上固化 tokenizer 版本与词表；服务端统一分词并缓存，防止前后端不一致。

 - 监控“token 膨胀率、OOV/byte 比例、上下文命中率”，定期回收低频子词或增补热词，控制延迟与成本。

## 4. 文本生成策略你实际怎么用？Greedy、Beam、Top‑k、Top‑p、温度、长度/重复惩罚——按场景说选择。
**一句话总结**
 
看任务要“准还是活”，准就用贪心/小束搜索配低温，活就用Top‑p/Top‑k配中等温度，再用长度/重复惩罚与停用词把控格式与冗余。

 **详细解释：** 

 - 追求确定性与可复现（抽取式问答、代码修复、规则回复） Greedy 或 Beam=2~5，temperature 0~0.3；长文本可加 length penalty≈1.0~1.2 做长度归一；禁止 n‑gram 重复。

 - 需要多样性与创意（文案、头脑风暴、改写） Top‑p 0.85~0.95 或 Top‑k 40~100（二选一即可，优先 Top‑p），temperature 0.7~1.0；repetition penalty 1.1~1.3 控制啰嗦。

 - 结构化/格式严格（SQL/接口schema/工具调用） Beam 小束 + 约束解码（正则/关键字/函数schema），必要时设 stop‑words 与最小/最大长度。

 - 长文/摘要（避免模式化与丢要点） Top‑p 0.9 + length penalty 1.0~1.2；若“覆盖不足”，可加 coverage/禁止重复三元组。

 - 实时与低延迟（对话、联机工具） Greedy 或 Top‑k 20~40（温度≤0.7）减少回溯；设置 early‑stop 与流式输出。

 - 统一落地建议 只选 Top‑p 或 Top‑k 其一；固定随机种子做A/B；按任务分环境保存“推荐参数模板”，并监控重复率、长度分布与人工可读性。

## 5. 长上下文怎么搞？Rope scaling、Position Interpolation、KV Cache 管理、检索增强、窗口注意力，你的实战方案是什么。
**一句话总结** 

 长上下文优先“检索+规划”控窗，再用“位置外推+稀疏注意力+KV 管理”把模型撑到更长——RAG 保相关，RoPE/PI 做外推，滑窗/块稀疏降复杂度，配合 KV cache 量化/淘汰与前缀复用，整体在命中率、延迟与显存之间平衡。

 **详细解释** 

 - 位置外推 RoPE scaling/NTK/YaRN：放大频率基数，推理直扩上下文；一般需小幅 SFT 校准以稳困惑度。

 - Position Interpolation（PI）：把长序列等比“压回”训练区间，推理端缩放位置再编码，稳定且易落地。

 - 选型：≤32k 先 RoPE‑scaling；更长配 PI 或二者叠加，小幅再训练做对齐。

 - 注意力与窗口 窗口/块稀疏（sliding‑window、local+global token、dilated）：复杂度从 O(L²) 降到近线性；对长文阅读/日志解析效果稳。

 - 关键 token 设为全局（标题、锚点、检索片段摘要）保证跨段依赖。

 - KV Cache 管理 前缀缓存/会话复用；KV 量化（int8/int4）与分片；淘汰策略（FIFO/LRU/基于注意力权重）；分段合并与去重。

 - 多轮对话做“摘要压缩历史+热点保留”，控制 KV 增长。

 - 检索增强（RAG） 文档切分（语义+结构）、召回（BM25+向量多路）、重排（cross‑encoder），只送 Top‑k 片段；片段去重与高亮引用。

 - 上下文规划：系统/工具/检索/用户/回复按配额放入，超窗先压低优先级段再做摘要。

 - 实战方案（落地顺序） 1）先上 RAG+上下文配额，解决相关性与成本； 2）再开 RoPE‑scaling/PI 做位置外推； 3）长文任务启用滑窗/块稀疏注意力； 4）KV 做量化+前缀复用+淘汰，监控显存与延迟。

 - 评估与监控 指标：检索命中率/引用准确率、长文 perplexity/QA 准确率、延迟与显存；分层看超长与常规场景。

## 6. KV Cache 在训练和推理中的差异是什么？它的加速价值有多大，吞吐与延迟你是如何权衡的，vLLM/paged‑attention 需要注意什么。
**一句话总结**
 
训练阶段基本不需要 KV Cache（整段并行、一次性算完带因果 Mask）；推理阶段分“prefill+decode”，在 decode 里复用历史 K/V 把每步复杂度从 O(L²) 降到 O(L)，长上下文下可带来数倍的时延下降与吞吐提升；权衡上用大批次/连续批处理提吞吐、用多查询注意力与KV量化/分页缓存控显存与尾延迟，vLLM 的 paged‑attention 需关注块大小、碎片/换页与调度策略。

 **详细解释** 

 - 训练 vs 推理 训练（teacher forcing）：整段并行自注意力+因果 Mask，没必要做逐步缓存；重点是高效内核（Flash‑Attention）、激活检查点等。

 - 推理：两阶段 Prefill：对提示串一次性算 Q/K/V（仍是 O(L²)），不复用。

 - Decode：逐 token 生成，复用历史 K/V，只与新 token 做 Q·Kᵀ，复杂度 O(L)，长上下文时单步时延可降 3–10×（视模型/显卡/实现）。

 - 加速与内存 KV 尺寸≈ layers × 2 × seq_len × kv_heads × head_dim × dtype；长上下文容易显存瓶颈。

 - 典型手段：Multi‑Query/Grouped‑Query Attention 降 kv_heads；KV 量化（int8/int4）降带宽/显存；分批 Prefill + 多路 Decode 连续合批。

 - 吞吐 vs 时延 吞吐靠大批次与连续批处理（continuous batching/merge decode steps）；但批次过大提升 next‑token latency。

 - 做 SLO 驱动的调度：限制每步总 token 数、混合短序优先；分开度量 prefill 吞吐与 decode TPS，监控 p50/p95。

 - vLLM/paged‑attention 注意点 分页 KV（block/page 例如 16/32 tokens）避免内存搬移，支持动态加入/退出请求；块太小→内核效率差，太大→碎片与浪费。

 - 关注碎片率/换页开销与 OOM：设最大上下文、KV 量化、必要时溢出到 pinned CPU 内存但要评估带宽。

 - 与张量并行/流水并行的兼容；Prefill/Decode 分离调度；校准 tokenizer 一致性与分块对齐。

 - 实用建议 先上 Flash‑Attn（prefill）+ KV cache（decode），配 MQA/GQA 与 KV int8；

 - vLLM 选合适 block size（16–64），打开连续批处理；

 - 以“tokens/s 与 p95 时延”为双目标做 A/B，结合业务 SLO 调整批量与最大上下文。

## 7. 推理加速这块你有哪些落地经验？量化、蒸馏、裁剪（INT8/INT4、AWQ/GPTQ、蒸馏目标/策略）分别带来了哪些收益和坑。
**一句话总结**
 
我按“先量化再小模型（蒸馏）最后做结构化裁剪”的顺序落地，INT8/INT4（AWQ/GPTQ）通常带来2–4×显存节省与1.3–2×时延下降；蒸馏用软标签/中间层/任务蒸馏把模型尺度直接降一档，延迟可再降30–60%；裁剪只做结构化（通道/头/FFN维度），在有内核支持时才有真实加速，整个过程用离线集+在线 A/B 双指标守住精度与稳定。

 **详细解释** 

 - 量化（首选权重量化，必要时激活一起） 方案与收益 INT8（SmoothQuant/AWQ/RTN）权重+激活：显存↓≈2×，时延↓≈1.2–1.5×；INT4（AWQ/GPTQ/TeQ）权重：显存↓≈4×，时延↓≈1.3–2×（依赖内核）。

 - KV cache 量化（int8/int4）在长上下文下收益很大（显存↓2–4×）。

 - 坑与对策 LLM 激活/头部有 outlier：做分组/每通道量化、SmoothQuant 或权重重标定；校准集覆盖指令/工具调用场景。

 - 仅权重量化对算力加速有限；需要 TensorRT‑LLM/ORT/MLC 等有低比特内核。

 - 评测除 PPL/准确率外，看校准(ECE)、鲁棒/越狱率与长上下文稳定性。

 - 蒸馏（把大模型“教小”） 目标与策略：logits 蒸馏（温度软标签）、中间层/注意力对齐、任务/奖励蒸馏（SFT/RLHF 后），可配 LoRA 减成本。

 - 收益：用 13B→7B/7B→3B 常见任务精度损失很小，时延再降30–60%，吞吐↑。

 - 坑：教师偏见与覆盖不足→高质量指令混合+难例采样；蒸馏只看 logits 容易丢推理链→加中间层/思维链监督。

 - 裁剪（只做“可落地加速”的结构化） 做通道/头/FFN 维度剪枝或低秩分解（SVD/LoRA‑merge），配蒸馏微调恢复精度；GPU 实得加速需内核支持（TensorRT‑LLM 支持通道维裁剪）。

 - 非结构化稀疏在通用 GPU 上通常“不加速”（内存受限），除非用 2:4/4:8 稀疏并有特定内核。

 - 实战流水线与验收 1）基线评测（离线任务集+在线分层指标）。 2）权重量化 INT8→INT4（AWQ/GPTQ），校准/回灌难例；必要时做 KV 量化。 3）小模型蒸馏（软标签+中间层/任务蒸馏），优先把模型档位直接降一档。 4）结构化裁剪+微调，确认部署内核支持后再启用。 5）上线用 tokens/s 与 p95/p99 延迟、成本/千 tokens、业务 KPI（GMV/转化/召回）做 A/B；异常回滚与灰度放量。

## 8. PEFT 方案里（LoRA/QLoRA/Prefix/Prompt‑Tuning/Adapter）你怎么选？说说稳定训练的经验。
**一句话总结**
 
默认选 LoRA；显存很紧或单卡上大模型选 QLoRA；想极低参数增量与热插拔按任务切换选 Adapter；只需快速小样本适配且不想改权重选 Prefix/Prompt‑Tuning；训练上统一走“小步长+分层冻结+稳健优化（bfloat16/clip/余弦衰减/适度dropout）”即可稳住收敛与效果。

 **详细解释** 

 - 如何选 LoRA：通用首选（Decoder/Encoder‑Decoder皆可），参数小、易合并权重，延迟增量小；多任务用不同 LoRA 权重热切换。

 - QLoRA：在 NF4/4bit 场景下做 LoRA 微调，单卡可带大模型；注意激活 outlier 与优化器稳定性。

 - Adapter（Houlsby/Pfeiffer/Parallel）：需要“可插拔模块化”或端上多任务共存时选；推理多一层感知到略增时延。

 - Prefix/Prompt‑Tuning（软提示）：想极小参数、极快适配且不改底座权重；对长上下文会额外占用 token，生成类任务更合适。

 - 典型超参与稳定训练 目标层：优先对 Q,K,V,O/FFN 投影做 LoRA/Adapter，保留 LN/Embedding 冻结；r=416，α≈832，dropout 0.05~0.1。

 - 学习率：LoRA/Adapter 1e‑4~2e‑4；Prefix/Prompt 1e‑3~1e‑2；warmup 3%~5%，余弦衰减；梯度裁剪 1.0。

 - 精度/显存：bfloat16 + Grad Checkpoint；QLoRA 用 NF4+双重量化，AdamW 8bit，必要时对 lm_head 保持 FP16。

 - 正则与稳定：Label Smoothing 0.05、权重衰减 0~0.1；混合难例/指令数据，避免过拟合单域；监控 ECE/毒性漂移。

 - 推理与部署：LoRA 可在线合并或按需加载；Adapter/Prompt 任务间热切；注意软提示长度对吞吐与成本的影响。

## 9. SFT 和对齐（RLHF/DPO/IPO/PPO）原理差在哪？在不同数据与资源条件下，你会怎么选路线。
**一句话总结**
 
SFT是在“有标准答案”的指令数据上做交叉熵模仿学习；对齐（RLHF/DPO/IPO/PPO）是在“有人类偏好”的反馈上优化行为，使模型更符合人意与安全，其中DPO/IPO直用偏好对训练，PPO需训练奖励模型再做策略优化、成本最高但可细粒度约束。

 **详细解释** 

 - 原理差异 SFT：用指令→答案的成对数据，最小化交叉熵，学“怎么答”；优点便宜稳，缺点是对齐有限、易过拟合标注风格。

 - DPO/IPO：用“偏好对（chosen, rejected）”直接优化logπ(chosen)−logπ(rejected)并加入KL约束（IPO对KL更稳），无需奖励模型，收敛快、性价比高。

 - RLHF（PPO）：先训奖励模型（用偏好对），再用PPO在KL约束下最大化奖励；可做奖励塑形、加入安全/合规条款，但算力和工程复杂度最高。

 - 何时选哪条路线 只有少量高质指令数据/预算有限：先做SFT（可配Label Smoothing、拒答模板与规则约束）。

 - 有成规模偏好对（几万对以上）、算力一般：首选DPO/IPO（实现简单、稳定性好），必要时小规模SFT热启动。

 - 需要可控的安全/多目标权衡（有安全奖励、风格奖励等）且算力充足：上RLHF（PPO），可分阶段做SFT→DPO→PPO。

 - 只有评分数据（打分而非偏好对）：先转成偏好对或训奖励模型再PPO；资源不足时做“打分回归+拒答惩罚”的简化版DPO。

 - 经验要点 数据优先级：高质覆盖>规模；偏好对需去重、控冲突样本；指令数据多样化与难例采样。

 - 训练细节：小学习率+KL/温度搜索；DPO/IPO注意参考策略冻结与长度归一；PPO要监控奖励黑化、KL漂移与有害率。

 - 评测：离线（赢选率、拒答率、毒性/幻觉、安全用例）+在线A/B（满意度、工单/转化），并做分层与区间估计。

## 10. RAG 系统你怎么设计？切分、索引、召回/重排、压缩/融合、兜底策略都怎么串起来。
**一句话总结**
 
RAG要把“高质量素材+稳健检索+可控注入”串成流水线：干净切分→多路索引→混合召回+强重排→压缩去噪→上下文配额融合→带引用回答，失败时扩大检索/回退模板，整体以可观测与评测闭环保稳定。

 **详细解释** 

 - 数据与切分 清洗去重、版本与权限标签；按语义/结构切分（段落/标题/表格单元），重叠 stride 20%~30%，生成摘要/关键词作辅助字段。

 - 索引 向量索引（FAISS/Milvus，bge/multilingual）+ 关键词索引（BM25）；存元数据（时间、来源、权限、主题）。

 - 召回与重排 查询改写/扩展（LLM或规则）→ 混合检索（BM25 ∪ 向量 ∪ 结构化）TopK → 交叉编码器/ColBERT 重排；域/权限过滤与去重。

 - 压缩与融合 片段压缩（LLM 抽取与句级截取）、信息去噪；上下文配额分区（系统/工具/检索/用户/回复），按重要度融合；高相似片段合并。

 - 生成与引用 提示模版：任务指令+检索片段（带来源）+格式约束+拒答准则；输出附带引用与置信度标签。

 - 兜底策略 低命中/低置信：放宽检索域→二次改写→外部搜索/知识库→模板答复/转人工；记录未命中样本回灌。

 - 评测与监控 指标：检索命中率@K、重排 MRR/nDCG、事实一致性/有害比、延迟与成本；在线 A/B 与反馈闭环（错答样本入训）。

 - 工程要点 片段去重与新鲜度；多索引分片与缓存；权限隔离；异常与超时降级；可观测（查询日志、召回/重排链路、引用命中）。

## 11. 向量库工程落地你遇到过哪些关键点？向量构造、相似度度量、检索速度/准确的平衡，分片副本与更新怎么做。
**一句话总结**
 
向量库要把“好向量+合适度量+可控ANN索引+可靠分片副本与热更新”一起做对；先把表征和度量定准，再在 HNSW/IVF‑PQ 等索引上按召回‑时延做参数权衡，最后用带过滤的分片/副本、增量 upsert 与压缩重建把线上稳定性兜住。

 **详细解释** 

 - 向量构造 统一 tokenizer/预处理，选与任务匹配的嵌入（如 bge/all‑MiniLM/领域模型）；维度合理（384/768/1024），必要时做PCA/OPQ降维。

 - 余弦相似度需单位化归一（L2‑norm=1）；做 MIPS 时可转余弦/加范数维。文本块切分带重叠，存标题/来源/时间等元数据。

 - 相似度度量 语义检索优先 cosine；图像/多模态看实际分布选 L2/dot；混合检索用 BM25 ∪ 向量，后接重排（cross‑encoder/ColBERT）。

 - 索引与速度‑准确权衡 HNSW：高召回、可在线插入；调 efConstruction/efSearch,M 上召回↔时延。

 - IVF/IVF‑PQ：大规模低内存，调 nlist/nprobe；PQ/OPQ 降存储与带宽但略降精度。

 - 评测看 Recall@K、nDCG、p95 延迟、QPS；离线网格搜索参数，线上分层A/B。

 - 过滤与多路召回 支持 metadata filter（权限/时间/类别）；先粗召回（BM25/HNSW/IVF）再精排；缓存热门 query 和重排结果。

 - 分片、副本与更新 按文档数或哈希做分片，副本≥2；写入走主分片，读走最近副本；一致性选 quorum/最终一致。

 - Upsert/删除：软删+定期 compact；批量导入与后台重建索引（rolling rebuild），版本化词表/嵌入器。

 - 在线更新：流式增量 + 异步重排；高频改动的分片单独扩容，冷热分层。

 - 存储与成本 启用压缩（PQ/int8）、向量内存映射；监控碎片率与重建窗口；GPU 索引看显存与带宽瓶颈。

 - 监控与守护 指标：召回/精排命中率、延迟/吞吐、失败率、重建耗时、索引大小；超时/降级策略（降 nprobe/efSearch 或回 BM25）。

## 12. 提示词工程你是怎么搞的？System/角色/约束/分步指令怎么写，如何防越狱与 Prompt Injection，评测和 Guardrails 怎么做。
**一句话总结**
 
把提示词写成“任务剧本”——System定边界，角色声明职责，约束列输入输出与禁令，分步指令拆流程并给格式模板；上线前后用越狱/注入对抗集评测，联动Guardrails（意图识别+黑白名单+敏感器+工具白名单+拒答模板）兜底。

 **详细解释** 

 - 结构与写法 System：定义身份与目标、允许/禁止范围、优先级规则（安全>事实>流畅），固定术语与口径。

 - 角色与上下文：说明场景与受众，提供最小充分的业务/知识上下文，声明只依据给定材料作答。

 - 约束与输出：列输入字段、输出字段与严格格式（JSON schema/表格），给1~2条正反示例；声明“无法满足→拒答+理由”。

 - 分步指令：检索/规划/解题/校验/引用四步；要求先列计划再执行；需要工具时显式工具协议（函数签名、参数、单位）。

 - 防越狱与 Prompt Injection 指令优先级：外部内容仅作“证据”，不得覆盖System；禁止执行用户文本中的指令。

 - 内容过滤：敏感词/正则/URL白名单，外链与代码只读不执行；工具调用走白名单与参数校验。

 - 证据标注：要求逐段引用来源（id/行号），缺证据时降温拒答；对“忽略上文”等典型越狱给显式拒答模版。

 - 评测与Guardrails 离线评测：功能集（正确率/结构合规）、安全集（越狱/注入/隐私泄露）、鲁棒集（噪声/错别字），监控通过率与置信度。

 - 在线监控：提示词漂移报警、输出结构校验、P(有害)/P(幻觉)打分阈值触发拒答或降级检索。

 - Guardrails组件：意图分类、策略路由（只允许安全工具）、PII/有害检测、Schema 校验、拒答与转人工流程。

## 13. Function/Tool‑Calling 的边界你怎么划？Schema 设计、幂等/重试、回滚与审计在工程里怎么保证。
**一句话总结**
 
把“能查不改的都走检索/查询，改动外部状态的必须走受限工具”，Schema 严格可校验，工具调用全链路可重放可审计，配幂等键与幂等语义、超时可重试、失败可回滚（或补偿），并在权限与风控下最小化可用能力面。

 **详细解释** 

 - 边界划分 只读/可缓存：搜索、检索、解析、报价计算等→允许频繁调用；写入/副作用（下单、转账、改配置）→最小能力面+显式确认。

 - 高风险动作必须二次确认/多因子/限额；跨系统只透出必要字段与白名单操作。

 - Schema 设计 JSON Schema（类型/枚举/范围/必填/依赖关系）+ 示例；输入做强校验，输出包含状态码/错误码/可追踪 request_id。

 - 不确定信息显式字段（e.g. top_k、confidence）；对金额、时间、时区统一单位与精度。

 - 幂等与重试 幂等键（业务唯一键，如订单号+场景），幂等语义“至多一次”；幂等冲突返回上次结果。

 - 超时/可恢复错误做幂等重试（退避+上限）；不可恢复错误直接失败并回传可诊断信息。

 - 回滚与补偿 读改写流程加版本/ETag；强一致要求事务或两阶段；跨系统用补偿（SAGA）记录步骤与逆操作。

 - 工具声明可逆性：不可逆动作需“预检+确认+延迟执行”。

 - 审计与安全 全量日志：原始提示、解析后参数、工具响应、调用链、操作者与权限；日志脱敏与签名防篡改。

 - 细粒度权限与配额；参数白名单/正则校验；输出/入参敏感词与PII检测；离线回放与沙箱压测。

 - 运行策略 超时/并发与熔断降级；冷/热点路由与缓存；灰度发布与回滚开关。

 - 监控SLO：成功率、p95延迟、重试率、幂等命中、补偿率，异常报警与自动化回收。

## 14. 做 Agent 时你怎么拆：Planner‑Executor、记忆、工具选路、反思/自纠错、任务分解；跟“直接问答”比有什么本质不同。
**一句话总结**
 
Agent=把“大模型”变成“可执行的流程体”，先用 Planner 拆任务、再由 Executor 依计划调用工具并写入记忆，结合路由/权限挑选合适工具，过程中做反思与自纠错迭代，直到达成目标；与直接问答不同，它强调可控计划、可观测行动和可复现结果。

 **详细解释** 

 - 拆分组件 Planner：解析意图→生成多步计划（检索/计算/调用API/汇总），给出中间产物与成功判据。

 - Executor：按计划逐步执行；每步结构化调用工具（函数调用/约束解码），拿到结果回写到上下文。

 - 记忆（Memory）：短期存放中间状态/证据，长期沉淀用户偏好与历史决策；读写要有权限与过期策略。

 - 工具选路（Routing）：基于意图/模式匹配/少样本示例选择工具；设白名单、速率限制与幂等键。

 - 反思/自纠错（Reflection）：检测冲突/空结果/置信度低时触发“复盘→改计划/换工具/重试”；记录失败样本回灌。

 - 任务分解：大任务→子任务 DAG；可并行的并发执行，不可并行的串行且设超时/回滚。

 - 与直接问答的本质差异 直接问答是一次性生成文本；Agent 是“计划+行动+观察+再计划”的闭环，强调可控性（Schema/权限）、可观测性（日志/审计）和可复现性（计划与工具轨迹）。

 - 落地要点 明确SLO与停止条件（成功判据/最大步数）；对外部副作用动作做确认与回滚；全链路日志与安全沙箱。

## 15. 大模型项目从架构角度怎么搭？模型选型（开/闭源）、推理框架（vLLM/TensorRT‑LLM/自研）、SLA、弹性与监控你怎么落地。
**一句话总结**
 
先以业务SLA为锚定容量与成本，再在“模型选型→推理内核→服务编排→弹性伸缩→可观测与治理”上做一体化设计：按场景选开/闭源+尺寸，推理层用 vLLM（长上下文/批处理）或 TensorRT‑LLM（低延迟/高算效），服务侧做网关路由、配额与A/B，结合队列深度/利用率做弹性，埋好时延/吞吐/稳定性全链路监控与灰度回滚。

 **详细解释** 

 - 模型选型 维度：任务类型（生成/工具/多模态）、数据合规与许可、上下文窗口、推理成本、可控性。

 - 策略：主力模型（如开源 7B/13B + QLoRA 域调优）+ 专用小模型（意图/安全/路由）；闭源（高质）补位关键场景或兜底。

 - 推理框架 vLLM：paged‑attention + 连续批处理，适合高吞吐与长上下文；注意 block size、碎片与KV配额。

 - TensorRT‑LLM：强内核优化与并行策略，低时延、算效高；适合线上低延迟/端侧/多并行拓扑。

 - 通用优化：Flash‑Attention（prefill）、MQA/GQA、KV 量化、prefix cache、流式输出。

 - 服务编排与治理 网关：鉴权、限流、配额、计费；路由：按意图/模型负载/成本做多模型调度与金丝雀发布。

 - 上下文层：RAG、工具调用、提示词模板与Guardrails（安全/PII/Schema 校验）；缓存（embedding/检索/响应）。

 - 契约：统一Tokenizer与token预算，定义SLO（p95/p99时延、成功率、tokens/s）。

 - 弹性与容量 维度：队列深度、GPU 利用率、tokens/s、KV 显存占用；HPA/自研调度按“prefill/decoding”分域伸缩。

 - 预热与冷启动：模型权重常驻/分片加载；故障迁移与跨可用区副本。

 - 可观测与运维 指标：请求成功率、p50/95/99 时延（prefill/decoder 分开）、吞吐（tokens/s）、OOM/重试率、KV 命中与碎片率、成本/千tokens。

 - 日志与审计：提示词版本、工具轨迹、错误栈；报警与自动降级（改模型、降上下文、关重排）。

 - 评测：离线基准 + 在线 A/B；灰度回滚与版本管理（模型/分词器/提示词）。

## 16. MoE 怎么玩更稳？门控、路由、稀疏激活的收益是什么，训练时怎么避免负载不均与专家塌陷。
**一句话总结**
 
MoE想稳，就用“温和路由+负载均衡约束+容量控制”的组合：Top‑2/Expert‑Choice 路由配噪声或温度，设置capacity factor与丢弃策略，叠加balance/entropy正则与专家归一化，训练期梯度/通信稳态化，基本可避免负载不均与专家塌陷，同时以稀疏激活换来更高参数规模与算效。

 **详细解释** 

 - 收益是什么 稀疏激活只计算少数专家（如Top‑2），在相同算力下扩大可训练参数量，提升困惑度/长期记忆；门控/路由让不同专家学到子分布，提升多域效果与算效。

 - 路由与门控怎么配 Gating：带噪声的softmax或温度缩放，常用Top‑2路由（Top‑1更快但易塌）；Expert‑Choice可由专家“挑样本”缓解不均。

 - Capacity factor：为每个专家设容量上限（如1.2×平均负载），溢出样本丢弃或回退到备选专家，保证显存与通信可控。

 - 防负载不均与专家塌陷 负载均衡损失（balance/importance loss）约束每个专家的被分配概率与实际流量接近均匀。

 - 路由温度/噪声：升温或加噪减少极端偏置；early phase可加大噪声，后期逐步退火。

 - Entropy 正则与专家偏置项（expert bias）避免单一专家吸流。

 - 规范化与稳定：expert FFN 前后加LayerNorm，梯度裁剪；小学习率/余弦衰减，必要时对gate单独lr。

 - 容量与丢弃策略：确定性排队+可重排；监控“丢弃率<1%”。

 - Expert Dropout/随机遮挡提升泛化，避免个别专家过强。

 - 工程要点 并行与通信：专家分片（expert parallel）+张量/数据并行，通信用All‑to‑All；优先选择本地/近邻专家减少带宽瓶颈。

 - 混精度与数值：bfloat16优先，gate用FP32；激活检查点降低显存。

 - 监控：每专家流量、丢弃率、balance loss、通信占比、OOM率；发现塌陷可调温度/噪声或重置少数专家。

 - 推理侧 固定Top‑1/2减少抖动；按请求特征做专家预选与缓存；保证路由与训练一致（温度/归一化）。

## 17. 安全合规你是怎么做的？幻觉检测/事实核查、内容审查、数据脱敏、审计，这些环节你都怎么串起来。
**一句话总结**
 
把安全合规做成“前置拦截→生成约束→后验审查→全链路审计”的流水线：请求侧做意图和PII拦截，生成侧用检索/引用与模板约束，产出后用事实核查与内容审核兜底，所有数据全程脱敏并可追溯。

 **详细解释** 

 - 前置拦截（输入侧） 意图识别与策略路由：高风险场景（医疗/法律/金融）强制走RAG/工具或拒答。

 - PII/敏感信息检测与脱敏（正则/模型），黑白名单、URL/代码只读不执行。

 - 生成约束（过程侧） 提示词安全约束：系统指令优先级>用户内容，模板化输出（JSON schema/引用必须）。

 - RAG+引用：答案基于可信检索片段，缺证据低温拒答；工具调用白名单+参数校验。

 - 后验审查（输出侧） 幻觉/事实核查：检索一致性打分、NLI/claim‑check，不达阈值则重写/降级检索/拒答。

 - 内容审核：涉政/涉黄/仇恨/暴力/自残等多类模型+规则融合；命中即改写或拦截。

 - 安全评测集与在线抽检：越狱/注入/有害样本持续回灌。

 - 脱敏与合规 存储与日志全量脱敏/分级加密；权限最小化与密钥轮换；数据留存与用途告知符合本地监管。

 - 审计与可观测 记录提示词版本、分词器、RAG片段、工具轨迹、判定分、人工介入；签名防篡改，可回放。

 - 指标：拒答率、有害率、事实一致性、引用命中、误杀率、p95时延与成本；异常自动降级与回滚。

## 18. 评测体系你怎么搭：离线（MT‑Bench/MMLU/BLEU/Rouge）到在线（用户反馈/工单解决率），一条流水线如何跑起来。
**一句话总结**
 
用“离线基准集+自动评分/回归”做准入，再以“灰度A/B+用户可观测指标”做线上验收，打通数据版本与模型/提示词版本，形成从评测→发布→回流的数据闭环。

 **详细解释**

离线先统一数据与版本（任务集、领域集、对抗安全集），指标按任务选用：MT‑Bench/MMLU、Exact‑Match/F1、BLEU/Rouge、代码/工具执行通过率、幻觉/安全打分；可用 LLM‑as‑Judge 但要设rubric与双评一致性，配回归集与阈值门槛，CI 里固定分词器/随机种子/提示词版本，过门后进入灰度。在线用金丝雀+A/B，核心看满意度/用户反馈、工单解决率、首响与p95时延、拒答/有害率、成本/千token，日志抽样做人审与错误回流；全链路记录评测版本与模型/提示词/检索片段，异常自动降级与一键回滚，定期把线上难例并入训练与离线集，形成持续评测与优化闭环。

## 19. 为什么只做 SFT 往往对不齐人类偏好？它跟预训练损失的差异到底体现在哪。
**一句话总结**
 
SFT只是在“有标准答案”的指令数据上做模仿学习（最小化交叉熵），优化的是“像标注一样写”，而人类偏好关心的是“哪种回答更好/更安全”的相对排序；因此仅做 SFT 往往对不齐偏好，需要用偏好学习（DPO/IPO/RLHF）在“相对优劣”上再优化。

 **详细解释** 

 - 预训练损失：在大规模语料上做语言建模，目标是预测下一个词，学到“可读分布”，不含价值判断与安全边界。

 - SFT 损失：对指令→答案最小化交叉熵，等价于“尽量贴近标注答案的逐词分布”，属于点对点模仿；数据覆盖不到的场景、冲突风格或含糊任务，模型容易“会答但不合人意”。

 - 偏好学习差别：DPO/IPO/RLHF 用“偏好对”或奖励，直接优化 chosen 优于 rejected 的相对概率（或奖励），把目标从“像标注”转为“人更喜欢/更安全”，能显著提升礼貌性、事实性与拒答策略。

## 20. 挑一个你深入研究过的模型（比如 DeepSeek‑R1/Llama/Mistral/Qwen），聊聊架构特性、训练技巧和使用心得。
**一句话总结**
 
Llama‑3 采用Decoder‑only、GQA/大词表与长上下文优化的现代架构，配合高质指令与偏好数据、稳健优化（bfloat16、Cosine、长warmup、Flash‑Attn），在推理用 vLLM+paged‑attention、KV 量化与LoRA/QLoRA 可覆盖多数业务，工程上要盯token化一致性与安全/检索模块协作。

 **详细解释** 

 - 架构特性 Decoder‑only Transformer，GQA（降低KV开销）、RMSNorm+SwiGLU，较大的词表与RoPE位置编码；训练用Flash‑Attention与大批次。

 - 训练技巧 数据：高质去重、多域指令+代码比例平衡；Mix 文本/对话/工具调用；偏好数据做DPO/IPO 提升对齐。

 - 优化：bfloat16、AdamW、Cosine LR、长warmup、梯度裁剪；LoRA/QLoRA 微调低成本扩展到垂直域。

 - 使用心得 推理：vLLM 连续批处理 + KV 量化 + prefix cache，长上下文启用 RoPE‑scaling/PI；

 - 结合RAG：切分/重排/引用与提示词模板；

 - 安全与可控：Guardrails与工具白名单，严格Schema；

 - 版本一致：固化 tokenizer/提示词与评测基线，避免“同模不同口径”。

## 21. 数据治理你怎么做？质量、去重、过滤、均衡怎么保证；分布漂移你如何监控并迭代。
**一句话总结**
 
数据治理做成流水线：采集→清洗→去重→质量评估→采样均衡→版本与权限→漂移监控与回流迭代；以自动规则+人工抽检双重把关，保证数据可追溯、可回滚、可持续演进。

 **详细解释** 

 - 质量与去重 规则：长度/语言检测、乱码/脏词/版权、HTML清理、敏感词；

 - 语义去重：MinHash/SimHash+LSH+阈值，跨源去重；消除模板与聚合页。

 - 过滤与均衡 领域/任务白名单；噪声过滤（困惑度阈值、规则/模型打分）；分层抽样平衡域、时间、语言、类别与正负比例。

 - 版本与追溯 数据版本化（元数据、来源、处理链）与权限分级；可回放的处理日志与审计，留存原始与成品双份。

 - 漂移监控 线上/离线分布对比：PSI/KL/KS、特征统计、OOV/byte‑rate、长度分布；告警阈值与窗口。

 - 评测闭环：难例/错答回流，定期增量更新；灰度评测后再合并主干。

 - 自动化与人审 规则+模型混合打分，阈值两侧自动处理，中间带人审；抽样验证通过率与一致性；

 - 指标：有效率、重复率、噪声率、领域覆盖、漂移分数、A/B 指标稳定性。

## 22. 当检索或对齐效果翻车时，你会用哪些兜底与增强手段？判空、fallback、多路召回、rerank、融合分别怎么用。
**一句话总结**
 
先把“命中率和置信度”量化好，命不中或低置信就触发兜底链路：判空→查询改写/扩展→多路召回（BM25+向量+结构化）→强重排→结果融合与压缩，仍不稳则走模板/FAQ/人工或直接拒答并回流难例。

 **详细解释** 

 - 判空与阈值：对召回@K、相似度、重排分、覆盖率设阈值；低于阈值即视为“检索失败/不可靠”。

 - Fallback 策略：优先走更稳的渠道（站内权威库→站外搜索）或模板/FAQ；高风险域直接拒答+引导，记录样本回流。

 - 多路召回：并行 BM25、向量（多模型嵌入）、结构化库与规则表；设分区/权限/时间过滤，TopK 去重。

 - Rerank：用 cross‑encoder/ColBERT 统一重排，必要时引入领域特征（时间、新鲜度、权威度）加权。

 - 融合与压缩：对多路结果做去重与投票/线性融合；长段先抽取关键句再注入，附来源与置信度。

 - 查询改写与扩展：同义改写、实体补全、意图纠错；对零命中/低命中重试一轮（限时限次）。

 - 生成侧保护：提示词要求“无证据低温拒答+逐条引用”；输出经内容安全与事实一致性校验不过即降级/重试。

 - 可观测与回流：全链路打点（命中率、低置信占比、fallback 命中、引用命中），错例自动入库，定期增量重建索引/更新召回器。
