### 问题描述：**为什么`fd=3`**
```bash
ubuntu_user@codeubuntu:~/shared_files/code/CPP$ ./tcp_server 
Server starting...
Socket created successfully, fd = 3
```
### 原因：
因为文件描述符 0、1、2 已经被系统预先占用：
- **0**：标准输入（stdin）
- **1**：标准输出（stdout）
- **2**：标准错误（stderr）
当程序调用 `socket()` 创建第一个套接字时，系统会分配当前可用的最小未使用文件描述符，即 **3**。
## 问题：二
```cpp
struct sockaddr_in server_addr;
memset(&server_addr, 0, sizeof(server_addr));
```
### 问题描述**为什么要用 `memset`**：
### 原因：
我们创建一个局部变量 `server_addr`，它的初始值是随机的（栈上的垃圾数据）。为了确保结构体中未使用的字段（如 `sin_zero`）是干净的，我们用 `memset` 将整个结构体清零。这是一种常见的防御性编程。
## 问题：三
```cpp
server_addr.sin_family = AF_INET;
server_addr.sin_port = htons(8080);
server_addr.sin_addr.s_addr = htonl(INADDR_ANY);
```
### 问题描述**为什么需要`htons`转换？**：
### 原因：
因为不同的 CPU 对多字节整数的存储顺序不同（小端或大端），而网络协议规定使用大端序。所以发送到网络的数据必须转换为网络字节序。htons可以将 16 位整数从主机字节序转换为网络字节序（大端）。

#  阶段二
## 问题：一
### 问题描述：如何让服务器**同时处理多个客户端**？
### 解决方法：
1. **多进程**：`fork` 一个子进程处理每个客户端，父进程继续等待新连接。
2. **多线程**：`pthread_create` 创建新线程处理每个客户端，主线程继续 `accept`。
3. **I/O 多路复用**：使用 `select`/`poll`/`epoll` 在一个线程内监听多个文件描述符。
## 问题：二
### 问题描述：为什么只用`g++ tcp_server.cpp -o tcp_server` 没有加`-pthread`也能编译成功：
### 原因：
从 glibc 2.34 开始，**pthread 库的函数被直接整合进了 libc 中**，因此编译时不再需要显式链接 `-pthread` 或 `-lpthread`。
## 问题：三
### 问题描述：为什么要用 epoll？
### 原因：
多线程模型虽然简单，但每个客户端需要一个线程，当并发连接数达到几千时，线程创建、切换、内存开销都非常大。  epoll允许一个线程同时监听数百、数千个 socket，只在 socket 就绪（有数据可读、可写等）时才去处理，从而避免了大量线程的浪费。epoll 是 Linux 特有的高效 I/O 多路复用机制，性能远高于传统的 select/poll。
## 问题：四
### 问题描述：为用Windows的cmd使用telnet输入HELLO在服务器上会显示Received from client: HReceived from client: EReceived from client: LLOReceived from client:
### 原因：
Windows 上用 `telnet` 连接服务器，输入 "HELLO" 时，服务器多次收到数据（逐字符），这是 Windows telnet 客户端的默认行为：**每键入一个字符就立即发送**，而不是等待回车后才发送整行。因此，服务器会多次调用 `recv`，每次收到一个字符（或少量字符），导致输出多次 `Received from client: `，而且由于没有换行，输出可能粘连在一起，看起来像是奇怪的拼接。
# 阶段三

## 问题：一
### 问题描述：为什么要学习边缘触发？
### 原因：
之前实现的是 epoll 水平触发（LT）模式： 只要 socket 接收缓冲区有数据，`epoll_wait` 就会持续通知。编程简单，即使你一次没读完，下次还会通知。
边缘触发（ET）模式：只在 socket 状态**发生变化**时通知一次（比如从无数据变为有数据）。 效率更高，减少了内核到用户态的事件拷贝次数。 但要求必须**一次性把数据读完**（循环读直到返回 `EAGAIN`），否则可能漏掉数据。 **必须搭配非阻塞 I/O**，否则如果数据没读完，下次不会再通知，程序就会永远阻塞在 `recv` 上。
## 问题：二
### 问题描述： 为什么要非阻塞？
### 原因：
在边缘触发模式下，当我们收到一个“可读”事件后，我们必须循环调用 `recv` 直到返回 `EAGAIN`（表示缓冲区暂时没有数据了）。  
如果 socket 是阻塞的，那么当缓冲区没有数据时，`recv` 会**阻塞**住，导致程序卡死，无法处理其他连接。  
所以必须用非阻塞模式，让 `recv` 在没数据时立即返回 `-1`，并设置 `errno = EAGAIN`，我们就可以据此停止读取。
## 问题：三
### 问题描述：监听 socket 为什么不用边缘触发？
### 原因： 
新连接事件是离散的，用 LT 更安全；如果使用 ET，每次有连接时只通知一次，若 `accept` 没处理完所有等待连接，可能会漏掉。用 LT 可以确保每次有连接就通知，直到队列为空。

## 问题：一
### 问题描述：为什么需要调优？
### 原因：
在 Linux 默认配置下，一个进程最多只能打开 1024 个文件描述符（包括 socket），而端口范围、TIME_WAIT 状态等也会限制并发连接数。要通过调整系统参数和内核参数，突破这些限制，让服务器能够处理成千上万的并发连接。
