### 2. 为什么选择 epoll 边缘触发而不是水平触发？边缘触发下如何确保数据完整读取？

**参考答案**  
> 边缘触发（ET）只在 socket 状态发生变化时通知一次（例如从无数据变为有数据），而水平触发（LT）只要缓冲区有数据就会持续通知。ET 可以减少内核到用户态的事件拷贝次数，在高并发场景下性能更高。  
> 为了保证数据完整读取，必须在 `EPOLLIN` 事件中 **循环调用 recv**，直到返回 `EAGAIN` 或 `EWOULDBLOCK`。同时，socket 必须设置为非阻塞模式，否则最后一次 recv 如果没有数据就会阻塞线程。我在代码中为每个连接设置了 `O_NONBLOCK`，并在读事件中写了 `while ((n = recv(...)) > 0) { ... }`，当 n < 0 且 errno 为 EAGAIN 时跳出循环。

### 3. 描述多线程 Reactor 模式中主线程和工作线程的职责，如何分配连接并避免锁竞争？

**参考答案**  
> 主线程只负责调用 `accept` 接收新连接，然后通过一个简单的轮询计数器（Round Robin）选择一个工作线程。主线程调用 `epoll_ctl` 将新连接的 socket 添加到目标工作线程的独立 epoll 实例中。`epoll_ctl` 本身是线程安全的，所以不需要额外加锁。  
> 每个工作线程独立运行自己的 `epoll_wait` 事件循环，处理属于自己的连接。一旦连接被分配给某个工作线程，后续所有的读写操作都在该线程内完成，线程之间没有共享数据，因此整个系统 **无锁**，避免了互斥锁带来的开销和死锁风险。

### 4. `sendfile` 零拷贝的原理与优势，如何处理大文件发送时的 `EAGAIN`？

**参考答案**  
> 传统 `read + write` 需要将文件数据从内核缓冲区拷贝到用户缓冲区，再拷贝回内核 socket 缓冲区，共 4 次拷贝。`sendfile` 允许在两个文件描述符之间直接传输数据，数据直接从内核页缓存拷贝到 socket 缓冲区，**绕过用户空间**，只需要 2 次 DMA 拷贝。  
> 优势是减少 CPU 拷贝次数、减少上下文切换、提高大文件传输效率。  
> 在非阻塞模式下，`sendfile` 可能返回 `EAGAIN` 表示发送缓冲区已满。我的实现中使用 `try_sendfile` 函数循环调用 `sendfile`，并更新偏移量和剩余长度。当返回 `EAGAIN` 时，函数返回 `false`，上层会监听 `EPOLLOUT` 事件，等 socket 可写时继续发送。同时通过 `header_sent` 标志区分响应头和文件体的发送阶段，形成状态机。

### 5. 你做了哪些系统调优？解释 `tcp_tw_reuse`、`ip_local_port_range`、`somaxconn`、`ulimit -n` 的作用。

**参考答案**  
> 为了让服务器支持更高的并发，我做了以下调优：  
> - `ulimit -n 1000000`：提高进程能打开的文件描述符上限，默认 1024 远远不够。  
> - `net.ipv4.tcp_tw_reuse=1`：允许重用处于 `TIME_WAIT` 状态的端口，可以快速回收端口资源，避免端口耗尽。  
> - `net.ipv4.ip_local_port_range="1024 65000"`：扩大客户端本地端口的范围，默认约 28k，改为 64k 后单客户端可以建立更多长连接。  
> - `net.core.somaxconn=4096`：增大 `listen` 的已完成连接队列长度，防止高并发下连接被丢弃。  
> `TIME_WAIT` 是主动关闭连接的一方进入的状态，持续 2MSL，作用是确保最后一个 ACK 能被对方收到并防止旧连接的数据包干扰新连接。`tcp_tw_reuse` 依赖 `tcp_timestamps`，适合客户端场景。

### 6. 如何测试出 6.4 万长连接？`wrk` 和 `ab` 的结果为何不同？

**参考答案**  
> 连接能力测试我使用了自研的高并发客户端，采用非阻塞 `connect` + epoll 事件驱动，能够快速建立大量连接。测试环境是同一局域网的两台虚拟机，服务器 2 核 4GB，客户端 2 核 2GB。通过调整 `ip_local_port_range` 和 `ulimit -n`，最终成功建立了 **63,976** 个长连接，接近单 IP 端口上限 64k，服务器文件描述符升至 63,993，CPU 占用仅 1.8%，内存约 9MB。

### 8. 解释 RAII，你在项目中如何应用？智能指针解决了什么问题？

**参考答案**  
> RAII（Resource Acquisition Is Initialization）是 C++ 的核心编程思想，利用对象的生命周期自动管理资源（内存、文件描述符、锁等）。资源在构造函数中获取，在析构函数中释放。  
> 在项目中，我使用 `std::string` 作为发送缓冲区，它的析构函数会自动释放内存；每个连接对应的 `client_info` 对象通过 `new` 创建，在工作线程中 `delete` 释放。虽然这里没有用智能指针，但完全符合 RAII 思想（`delete` 在析构时执行）。  
> 智能指针（`unique_ptr`、`shared_ptr`）可以避免手动 `delete` 导致的内存泄漏。`unique_ptr` 独占所有权，适合管理单个连接信息；`shared_ptr` 通过引用计数共享资源，配合 `weak_ptr` 可以解决循环引用问题（例如父子节点互相持有）。

### 11. 你的服务器中使用了 `std::string` 作为发送缓冲区，在多线程环境下是否安全？如果多个线程同时向同一个 socket 写数据，你会怎么设计？

**考察点**：C++ 容器线程安全性、多线程并发设计。

**参考回答**  
`std::string` 本身不是线程安全的，但我的设计中每个 socket 只属于一个工作线程，因此对同一个 `send_buffer` 的访问是单线程的，不存在竞争。

### 12. 你的 epoll 事件循环中，如果 `recv` 返回 0 表示对方关闭连接，但你在关闭连接前为什么要先从 epoll 中删除？不删除会怎样？

**考察点**：epoll 使用细节、文件描述符生命周期。

**参考回答**  
需要先调用 `epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL)` 再从 epoll 实例中删除，然后再 `close(fd)`。  
如果不删除，当文件描述符关闭后，epoll 内核事件表中仍然残留该 fd，后续 `epoll_wait` 可能会返回 `EPOLLHUP` 或 `EPOLLERR` 事件，导致程序尝试对已关闭的 fd 操作，可能引发崩溃或逻辑混乱。所以标准做法是先删除再关闭。

### 14. 你的服务器是如何处理 `TIME_WAIT` 状态的？有没有遇到过端口耗尽的问题？怎么解决的？

**考察点**：TCP 状态机、系统调优、问题定位能力。

**参考回答**  
在压测初期，我遇到过端口耗尽问题。服务器作为主动关闭连接的一方（因为响应中带 `Connection: close`），每次请求后会进入 `TIME_WAIT` 状态，持续 60 秒。当短连接请求频率很高时，本地端口（约 28k 个）被占满，新连接无法建立。  
我通过以下方式解决：  
1. 启用 `tcp_tw_reuse=1`，允许重用处于 `TIME_WAIT` 的端口（需要配合 `tcp_timestamps`）。  
2. 扩大本地端口范围 `ip_local_port_range="1024 65000"`，增加可用端口数量。  
3. 在后续版本中，支持 HTTP/1.1 长连接，让客户端主动关闭连接，减少服务器进入 `TIME_WAIT` 的次数。

### 17. C++ 中 `vector` 的 `push_back` 和 `emplace_back` 有什么区别？在你的项目中哪里可以用到？

**考察点**：C++11 特性、性能优化。

**参考回答**  
`push_back` 接受一个已有对象，会调用拷贝或移动构造函数；`emplace_back` 接受构造对象的参数，直接在容器内原地构造，避免了临时对象的拷贝或移动。  
例如，向 `vector<client_info>` 中添加元素时，如果用 `push_back`，需要先构造临时对象再拷贝；而 `emplace_back` 可以直接传入构造参数（如 `fd, ""`），效率更高。在我的项目中，虽然没有直接使用 `vector` 存储连接（用数组索引），但在其他数据结构中可以用 `emplace_back` 提升性能。

### 18. 解释一下你理解的“Reactor”模式，它和“Proactor”模式有什么区别？你的服务器属于哪种？

**考察点**：网络设计模式。

**参考回答**  
Reactor 模式是一种基于事件驱动的设计，应用程序注册感兴趣的事件（如读、写），事件循环（`epoll_wait`）检测到事件后，回调相应的处理函数（读、写）。它是同步非阻塞的，应用程序主动读写数据。  
Proactor 模式则是异步 I/O，应用程序发起读写操作后立即返回，操作系统完成数据拷贝后通知应用程序。Windows 的 IOCP 是典型实现，Linux 上的 io_uring 也可以实现类似 Proactor 的行为。  
我的服务器是 **Reactor 模式**，因为主循环调用 `epoll_wait` 等待事件，收到可读事件后主动 `recv`，收到可写事件后主动 `send`，是同步非阻塞方式。

### 19. 如果线上服务器突然 CPU 飙升到 100%，你如何排查问题？你会使用哪些工具？

**考察点**：线上问题排查能力。

**参考回答**  
我会按以下步骤排查：  
1. `top` 或 `htop` 查看是哪个进程占用了 CPU。  
2. `top -H -p <pid>` 查看进程内的线程 CPU 占用，确定是否是工作线程或某个线程死循环。  
3. 使用 `perf top -p <pid>` 实时查看热点函数，定位是系统调用还是业务逻辑。  
4. 如果是业务逻辑，可以生成火焰图：`perf record -g -p <pid> sleep 30; perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg`，分析调用栈。  
5. 检查是否有死循环、频繁的锁竞争（可用 `pstack` 多次查看线程堆栈是否卡在同一个地方）。  
6. 如果怀疑是网络事件过多，可以用 `strace -c -p <pid>` 统计系统调用次数。  
7. 对于内存问题，可用 `valgrind` 或 `AddressSanitizer` 检测内存泄漏。

**考察点**：求职动机、学习热情、职业规划。

**参考回答**  
技术上，我计划深入学习分布式系统（如 Raft、Paxos）、高性能网络库（如 brpc、seastar）、以及 C++20/23 新特性（协程、module）。同时，我会继续关注 AI 工程化方向，探索 AI 辅助开发（vibe coding）在大型项目中的应用。  
对于实习岗位，我希望能加入一个技术氛围浓厚、有挑战性项目的团队，参与后端系统的开发，尤其是高性能、高可用方向。我愿意从基础做起，快速学习业务和技术，争取在实习期间做出实质性贡献。我相信我的项目经验和自驱力能够让我快速融入团队。
