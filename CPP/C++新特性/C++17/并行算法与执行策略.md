# 并行算法与执行策略（C++17，C++20 增强）

**一句话定义**：并行算法允许标准库算法以并行方式执行，通过在执行策略中指定调度方式（顺序、并行、向量化），使开发者无需手动管理线程即可利用多核 CPU 和 SIMD 指令集，显著提升数据处理类任务的性能。


## 详细语法与用法

### 执行策略类型与对象

执行策略定义在 `<execution>` 头文件中，包含以下类型和对应的全局对象[reference:0][reference:1]：

| 策略类型 | 全局对象 | C++ 版本 | 核心特性 |
|----------|----------|----------|----------|
| `sequenced_policy` | `std::execution::seq` | C++17 | 强制顺序执行，与传传统算法行为一致[reference:2] |
| `parallel_policy` | `std::execution::par` | C++17 | 多线程并行执行，每个线程内元素访问按顺序进行 |
| `parallel_unsequenced_policy` | `std::execution::par_unseq` | C++17 | 多线程并行 + 单线程内 SIMD 向量化，最高性能潜力[reference:3] |
| `unsequenced_policy` | `std::execution::unseq` | C++20 | 单线程内 SIMD 向量化，不启用多线程[reference:4] |

**关键区别**：
- `seq`：单线程顺序执行，与无策略的传统调用等价。
- `par`：多线程并行，元素访问顺序在全局上是**未指定的**（但单个线程内仍保持顺序）。
- `par_unseq`：多线程并行 + 每个线程内可能将迭代操作向量化，允许元素访问在单个线程内也**互不排序**，约束最强。
- `unseq`（C++20）：仅向量化，不创建额外线程[reference:5]。

### 基本使用示例

```cpp
// C++17 并行排序：只需在第一个参数传入执行策略
#include <algorithm>
#include <execution>
#include <vector>

int main() {
    std::vector<int> vData = {1, 3, 5, 7, 2, 4, 6};
    
    // 顺序执行（传统方式）
    std::sort(vData.begin(), vData.end());
    
    // 并行执行（C++17 新增）
    std::sort(std::execution::par, vData.begin(), vData.end());
    
    // 并行 + 向量化执行（更高性能要求时使用）
    std::sort(std::execution::par_unseq, vData.begin(), vData.end());
}
```

### 支持并行化的主要算法

C++17 明确要求以下算法支持执行策略重载[reference:6][reference:7]：

- **排序类**：`std::sort`、`std::stable_sort`
- **遍历类**：`std::for_each`、`std::for_each_n`
- **归约类**：`std::reduce`、`std::transform_reduce`（C++17 新增）
- **扫描类**：`std::exclusive_scan`、`std::inclusive_scan`（C++17 新增）
- **变换类**：`std::transform`
- **拷贝/填充类**：`std::copy`、`std::fill`
- **查找类**：`std::find`、`std::find_if`、`std::search`

> **注意**：`std::unique`、`std::partition`、`std::nth_element` 等算法在标准中仅“鼓励实现支持”，实际是否并行取决于 STL 实现（如 libstdc++ 12+ 和 libc++ 14+ 才逐步补全）[reference:8]。

### 实用代码示例

```cpp
#include <execution>
#include <vector>
#include <algorithm>
#include <numeric>
#include <iostream>

int main() {
    // 1. 并行 for_each：对每个元素执行操作
    std::vector<int> data(1000000, 1);
    std::for_each(std::execution::par, data.begin(), data.end(),
                  [](int& x) { x = x * 2 + 1; });
    
    // 2. 并行 transform：将一组数据转换为另一组
    std::vector<int> input(1000000, 2);
    std::vector<double> output(input.size());
    std::transform(std::execution::par_unseq, input.begin(), input.end(),
                   output.begin(),
                   [](int x) { return std::sqrt(static_cast<double>(x)); });
    
    // 3. 并行 reduce：求和（注意顺序敏感）
    double sum = std::reduce(std::execution::par, data.begin(), data.end(),
                             0.0, std::plus<>{});        // 与 std::accumulate 类似但可并行[reference:9]
    
    // 4. 并行 transform_reduce：先变换再归约
    auto result = std::transform_reduce(std::execution::par_unseq,
                                        input.begin(), input.end(),
                                        0, std::plus<>{},
                                        [](int x) { return x * x; });
}
```


## 底层原理与实现机制

### 1. 执行策略作为编译期标记

执行策略对象（`seq`、`par`、`par_unseq` 等）是**空类型标记对象**，不包含运行时数据。它们仅用于编译期重载决议——算法的不同重载版本通过区分执行策略类型来提供不同的实现[reference:10]。由于这些对象无状态，它们的拷贝成本为零，只是编译器的指示器。

### 2. 并行算法的典型实现模式

标准库实现的并行算法通常依赖以下底层技术：

| 执行策略 | 底层技术 | 实现复杂度 |
|----------|----------|------------|
| `seq` | 直接顺序执行，不做任何特殊处理 | 极低 |
| `par` | 线程池（如 Intel TBB）或 `std::async` 分块执行 | 中等 |
| `par_unseq` | 线程池 + 编译器 SIMD 指令（如 AVX）自动向量化 | 较高 |

- `par` 策略将数据范围分割为若干块，每个块由单独线程处理，线程间无顺序约束。典型实现使用线程池避免重复创建线程的开销。
- `par_unseq` 在 `par` 的基础上，允许编译器对单个线程内的循环进行**向量化**（将多个数据同时加载到向量寄存器中并行计算）。这意味着对元素的访问不仅可能在不同线程间乱序，还可能在单个线程内乱序，因此对操作的要求最为严格[reference:11]。

### 3. 对用户代码的约束原理

当使用非 `seq` 策略时，开发者向编译器传达了两个重要信息[reference:12]：

1. **期望并行**：开发者希望（但不要求）算法并行执行。具体实现可能根据数据规模和系统负载忽略该提示，退化为顺序执行。
2. **代码安全**：开发者保证传递给算法的操作（如 lambda、函数对象）是线程安全的，不会引入数据竞争。

### 4. 并行算法的复杂性影响

并行算法在运行时会执行更多的核心操作（元素交换、比较、函数对象调用等），但其总耗时反而可能减少——这是通过并行化分摊工作、增加并行度来抵消开销的结果[reference:13][reference:14]。代价是并行版本可能在某些输入规模下产生额外的内存分配和同步开销。

### 5. 异常处理机制

当在并行算法执行期间，元素访问函数通过未指定的异常退出时，标准库会调用 `std::terminate`。具体实现可以定义其他执行策略来处理异常，但标准仅提供这一种保证[reference:15]。这意味着并行算法不适合用于抛出异常的场合。

### 6. 平台异构执行（超越 CPU）

理论上并行算法可以实现在 GPU 等异构设备上执行，但 C++17 标准本身未对此进行规定。NVIDIA 的 HPC 编译器（NVC++）是实际案例之一，它支持将 `std::execution::par` 和 `std::execution::par_unseq` 算法编译为在 GPU 上执行[reference:16]。这表明并行算法的概念具有扩展到更多硬件类型的潜力。


## 与相关特性的对比

### 1. 四种执行策略对比

| 策略 | 多线程并行 | SIMD 向量化 | 元素访问顺序 | 适用场景 |
|------|------------|-------------|--------------|----------|
| `seq` | ❌ | ❌ | 全局顺序 | 调试、小数据集、有强依赖关系 |
| `par` | ✅ | ❌ | 线程间未指定，线程内顺序 | 中到大型数据，有顺序敏感性 |
| `par_unseq` | ✅ | ✅ | 完全未指定（线程间+线程内皆无序） | 超大数据，纯函数式操作，无副作用 |
| `unseq`（C++20） | ❌ | ✅ | 线程内未指定 | 单核环境，榨取单核向量化性能 |

### 2. 并行算法 vs 手动多线程

| 方面 | C++17 并行算法 | 手动 `std::thread` |
|------|----------------|-------------------|
| 代码量 | 极少（只需加一个策略参数）[reference:17] | 需要编写线程函数、任务分割、同步代码 |
| 性能调优 | 由标准库实现负责 | 完全手动控制 |
| 异常安全 | 遇到异常可能 `std::terminate`[reference:18] | 完全可控 |
| 适用场景 | 数据并行任务（独立处理元素） | 任务依赖复杂、需要精细控制同步的任务[reference:19] |
| 线程数控制 | 不可控（由实现决定） | 完全可控 |

### 3. 并行算法 vs C++11 `std::async`

`std::async` 是单次异步任务的更高层级抽象，而并行算法是**批量数据并行**。两者并非替代关系：
- `std::async` 适合独立的异步操作（如一次网络请求、一个独立计算任务）。
- 并行算法适合对容器所有元素批量应用同一操作（如对 1000 万个点计算坐标变换）。
- 并行算法的内部实现可能使用 `std::async` 分发任务，但这是实现细节。


## 常见面试问题与解答

### 问题 1：`std::execution::par` 和 `std::execution::par_unseq` 的核心区别是什么？什么时候用哪个？

**答**：两者都启用多线程并行，但 `par_unseq` **额外允许编译器在单线程内进行 SIMD 向量化**[reference:20]。`par` 仅保证线程级并行，单个线程内元素访问保持顺序；`par_unseq` 允许访问在单个线程内也互不排序，这给编译器更大的向量化优化空间。

**选择原则**：
- 若操作**顺序敏感**（如修改共享计数器、依赖前序迭代结果），必须用 `par`。
- 若操作**无副作用且可重排**（如累加、求最大值、`std::transform` 中的纯函数），使用 `par_unseq` 可获得更高性能[reference:21]。

**错误示例**：对含 `std::cout` 或 `push_back()` 到同一容器的操作盲目使用 `par_unseq` 会导致输出乱序和数据竞争[reference:22]。

---

### 问题 2：并行算法是否保证一定并行执行？如果不保证，如何判断是否真的并行？

**答**：**不保证**。执行策略只是一个“提示”（hint），实现可以根据数据规模、系统负载等因素选择退化为顺序执行[reference:23]。标准库可以忽略并行提示，只要行为正确即可。

**验证方法**[reference:24]：
1. 用系统监视工具（如 `htop`、任务管理器）观察 CPU 多核占用率是否飙升。
2. 在 lambda 中加入带时间戳的日志（注意线程安全，使用 `std::mutex` 或原子计数器）。
3. 对比不同策略下 `std::chrono::steady_clock` 的耗时变化。
4. 某些实现（如 Intel TBB 后端）提供调试接口。

---

### 问题 3：为什么我用了 `std::execution::par`，程序反而更慢？

**答**：这是最常见的并行陷阱。并行化并非总是带来性能提升，主要原因如下[reference:25][reference:26]：

| 原因 | 说明 | 阈值参考 |
|------|------|----------|
| **数据规模太小** | 并行化开销（线程创建/同步/任务拆分）远超计算本身 | 少于数千个元素时效果不佳 |
| **操作过于轻量** | 每元素操作极简单（如 `x * 2`），并行开销占主导 | 需数千甚至数万元素才体现收益 |
| **迭代器非随机访问** | 如 `std::list` 上用 `std::for_each`，大部分实现会退化为串行 | 容器类型至关重要 |
| **内存带宽瓶颈** | 大量 cache-unfriendly 的随机读写，CPU 计算并非瓶颈 | 需分析内存访问模式 |

**建议**：先用串行版本跑基准测试，确认数据规模超过阈值后才尝试并行，并用 `std::chrono` 实测对比。并行算法启动开销通常在几百微秒级，少于 10k 元素时可能吃掉全部收益[reference:27]。

---

### 问题 4：在并行算法中使用的 lambda 有什么限制？为什么？

**答**：使用 `par` 或 `par_unseq` 时，lambda 必须**不能引入数据竞争**和**死锁**[reference:28]。具体要求如下：

| 限制 | 原因 |
|------|------|
| 不能修改非原子共享变量 | 多线程同时访问同一内存导致数据竞争 |
| 不能依赖特定执行顺序 | 并行算法中元素访问顺序不确定 |
| 不能调用非线程安全的函数（如 `std::cout`） | 标准库输出流非线程安全，并发写入会乱序或崩溃 |
| `par_unseq` 下不能调用向量化不安全的操作（如 `std::atomic`）[reference:29] | 向量化会让同一线程内的操作交错执行，原子操作语义被破坏 |

`par_unseq` 的约束比 `par` 更严格：它要求操作不能调用任何向量化不安全的函数[reference:30]。这是因为向量化会将多个迭代操作重叠执行，导致同步原语（如 `std::atomic`）无法正常工作。


## 典型错误与最佳实践

### ❌ 典型错误

#### 错误 1：小数据集上盲目并行

```cpp
std::vector<int> small_vec = {1, 2, 3, 4, 5};
// ❌ 并行开销大于计算收益，反而更慢
std::sort(std::execution::par, small_vec.begin(), small_vec.end());
```

**正确做法**：仅当数据规模超过阈值（通常数千元素）时才考虑并行。

---

#### 错误 2：lambda 中存在数据竞争

```cpp
int counter = 0;
std::vector<int> data(1000000);
// ❌ 多线程同时修改 counter，数据竞争，未定义行为
std::for_each(std::execution::par, data.begin(), data.end(),
              [&counter](int) { ++counter; });
```

**正确做法**：使用 `std::atomic<int>` 或 `std::mutex` 保护共享状态[reference:31]。

---

#### 错误 3：`par_unseq` 中使用非向量化安全的操作

```cpp
// ❌ par_unseq 中调用 std::cout（非向量化安全，且线程不安全）
std::for_each(std::execution::par_unseq, data.begin(), data.end(),
              [](int x) { std::cout << x << "\n"; });
```

**正确做法**：仅当操作无副作用且可向量化时使用 `par_unseq`。

---

#### 错误 4：遗漏 `<execution>` 头文件或策略位置错误

```cpp
#include <algorithm>
// ❌ 缺少 #include <execution>
std::sort(std::execution::par, v.begin(), v.end());  // 编译错误

// ❌ 策略位置不正确（应该作为第一个参数）
std::sort(v.begin(), v.end(), std::execution::par);
```

**正确做法**：包含 `<execution>` 头文件，策略作为第一个参数传入[reference:32]。

---

#### 错误 5：依赖元素处理顺序

```cpp
std::vector<int> data = {1, 2, 3, 4, 5};
std::vector<int> result(data.size());
// ❌ 假设后一个元素依赖于前一个的结果
std::transform(std::execution::par, data.begin(), data.end(), result.begin(),
               [prev = 0](int x) mutable { return prev += x; });  // 未定义行为
```

**正确做法**：并行算法中不应依赖元素间的顺序。对于顺序依赖的归约，使用 `std::inclusive_scan`（支持并行）或保持顺序执行。

---

### ✅ 最佳实践

| 实践 | 说明 |
|------|------|
| **大数据优先并行** | 仅在数据规模超过数千甚至数万时才考虑并行策略[reference:33] |
| **优先选择 `par`** | `par` 是最常用的策略，适用范围最广；`par_unseq` 仅在操作纯函数且性能要求极高时使用[reference:34] |
| **避免在 lambda 中使用 I/O 和同步原语** | 输出操作和锁会严重拖累并行性能 |
| **使用纯函数式操作配合 `par_unseq`** | 无副作用的操作（如 `x*x`、`std::sqrt`）可获得最佳加速 |
| **用 `std::chrono` 实测对比** | 不要凭感觉猜测并行是否生效，用数据说话[reference:35] |
| **调试时先用 `seq`** | 串行版本行为确定，便于断点调试；上线前再切换策略[reference:36] |
| **注意编译器和库版本** | 某些实现需要额外链接选项（如 GCC 需要 `-ltbb` 或 `-fopenmp`）[reference:37] |

**验证并行是否生效的实用方法**[reference:38]：
1. 用系统监视工具观察 CPU 多核占用率是否飙升。
2. 在 lambda 中加入带时间戳的日志（注意线程安全，使用 `std::mutex` 或原子计数器）。
3. 对比不同策略下 `std::chrono::steady_clock` 的耗时变化。
4. 某些实现（如 Intel TBB 后端）提供调试接口。

```cpp
// 好的示例：大数据集上的纯函数 transform
std::vector<double> input(10'000'000);
std::vector<double> output(input.size());
std::transform(std::execution::par_unseq, input.begin(), input.end(),
               output.begin(), [](double x) { return std::sqrt(x); });

// 好的示例：先实测再决定策略
auto seq_time = measure_time([&] { std::sort(std::execution::seq, v.begin(), v.end()); });
auto par_time = measure_time([&] { std::sort(std::execution::par, v.begin(), v.end()); });
if (par_time < seq_time * 0.8) { /* 采用并行 */ }
```


## 编译器支持与版本演进

| 标准 | 主要增强 | 编译器最低版本（完整支持） |
|------|----------|--------------------------|
| **C++17** | 引入 `seq`、`par`、`par_unseq` 三种执行策略及并行算法重载 | GCC 9+（需 `-ltbb`）、Clang 7+（需 TBB）、MSVC 2019 16.10+ |
| **C++20** | 引入 `unseq`（单线程向量化策略） | GCC 10+、Clang 12+、MSVC 2019 16.11+ |

**重要注意事项**：

1. **GCC/libstdc++**：并行算法实现依赖 Intel TBB 或 OpenMP，需要额外链接 `-ltbb` 或 `-fopenmp`[reference:39][reference:40]。
2. **Clang/libc++**：对并行算法的支持较晚，部分版本可能不完整，建议查阅实现文档[reference:41]。
3. **MSVC**：仅支持 `par` 策略，且需 `/Qpar` 编译选项[reference:42]。
4. **特性测试宏**：`__cpp_parallel_algorithms` 表示支持并行算法（C++17 值：201603）。

```cpp
// 编译示例（GCC）
g++ -std=c++17 -ltbb main.cpp -o main

// 编译示例（MSVC）
cl /std:c++17 /Qpar main.cpp
```

**执行策略是 C++17 中并行 STL 的核心抽象**，它以极低的代码侵入性带来了显著的多核性能提升，是面试中高频考察的现代 C++ 特性。掌握其策略选择、性能特征和约束条件，是在实际项目中正确使用这一特性的关键。
